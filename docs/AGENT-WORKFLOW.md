# Optional agents

Canopy remains a planner. Project connections, imported specifications and agent runs are optional. Saving a connection, changing a workflow status or editing a specification never dispatches work.

## Live build experience

Open **Project options (⋯) → Agent connection → Build effects** for **Build graphics** and **Build sound**. Both default off and save immediately for all projects in this browser, independently of saving the repository connection. The settings share one browser-local preference provider with the build window, including synchronization between browser tabs. Implementation dispatch and active implementation history use the same reactor for Codex, Claude and Gemini. The experience consumes the existing run resource (`state`, `output`, session/workspace presence and result); no agent HTTP contract, execution policy, database schema or task status changes are involved. Decorative motion indicates an active worker; pulses indicate changed retained output. There are no timed planning/build/testing phases, synthetic commands, success assumptions or progress percentages.

The view opens for an active implementation and can be reopened with **View build**. Sound is unlocked from an explicit UI gesture, has an independent remembered mute setting, stops with the view, and never replays historical completion cues. Closing or disabling the experience does not cancel work. The view retains **Stop run**, reports failed/cancelled/interrupted states, and pauses motion and sound when polling fails. Refreshing agent activity reconciles the saved run after reconnecting. Canvas/audio resources are released when the view/task closes; background and reduced-motion presentations avoid continuous animation.

## Local execution contract

- A project connection records its repository directory, base Git ref, preferred provider, optional model and instructions. These are explicit user inputs. It is a local code workspace binding; it does not claim to create or synchronize vendor app project containers.
- `spec` and `documentation` runs have read-only tools and return Markdown for review, import or download. `implementation` runs work in a detached Git worktree created from the configured ref. They retain changes for review and do not merge or deploy.
- Each explicit request has a unique `requestId`, project `expectedRevision`, provider, purpose, instructions and optional previous run ID. Retrying that same request returns the original run. Concurrent attempts on the same task are rejected.
- A run captures the persisted task title/specification, connection settings and project revision. Editing the live task never changes a captured work order. Resume is allowed only for the same task, provider and purpose, using its exact saved session and workspace.
- Run state is independent of task workflow status: queued, running, cancelling, succeeded, failed, cancelled or interrupted. Success means the agent completed; it does not mean the work passed review. No workflow status is automatically updated.
- Cancellation terminates the process tree. Restart marks unfinished work interrupted; it never silently replays a task. Missing tools, credentials, refs and repository paths produce explicit failures.
- Runs and connections persist in native DuckDB through `IWorkspaceStore`. Run output is bounded by configured limits. Agent endpoints accept only local, same-origin browser requests. Credentials stay with the installed CLIs.

## HTTP interface

All routes are below `/api/agents` and use JSON/problem responses. Reads return the resource rather than a workspace snapshot.

| Method | Path | Contract |
| --- | --- | --- |
| GET | `/providers` | Configured executables, installation availability and UI polling interval; installation is not authentication evidence |
| GET | `/projects/{id}/connection` | Connection or null; 404 for an absent project |
| PUT | `/projects/{id}/connection` | Save `{expectedRevision, repositoryPath, baseRef, provider, model, instructions}`; validate the Git workspace; return the connection |
| DELETE | `/projects/{id}/connection?expectedRevision=…` | Disconnect; preserve historical runs; return null |
| GET | `/tasks/{id}/runs` | Run history, newest first |
| POST | `/tasks/{id}/runs` | Explicit dispatch with `{requestId, expectedRevision, provider, purpose, instructions, previousRunId?}`; return persisted run; duplicate request IDs return the same run |
| GET | `/runs/{id}` | Captured work order, state, session, workspace, progress, result and diff |
| POST | `/runs/{id}/cancel` | Idempotent cancellation; return current run |

Stale project revisions and already-active tasks return 409. Invalid bindings, blank work orders, mismatched resumes and unknown providers/purposes return 400. A missing configured executable returns 503. Project/subtree deletion is rejected while affected runs are active. Historical run rows are removed with explicitly deleted tasks/projects; worktree files are retained.

Markdown import uses the same Tiptap codec as MCP, previews before append/replace and saves through the normal revision-checked task API. Agent output is never automatically imported. Documentation may be downloaded as Markdown independently of the task specification.

## Choosing the repository folder

`POST /folder-picker` with `{start}` opens the operating system's folder dialog on the machine running the backend, which in phase 1 is the same machine as the browser, and waits for a choice. It returns `{path}` with the chosen absolute folder, or `{path: null}` when the dialog is cancelled. `start` is used as the dialog's starting folder only when it is an existing absolute directory. On macOS the backend uses `osascript`. Other platforms need `Agents:FolderPickerExecutable` and `Agents:FolderPickerArguments`: the command must print the chosen path, exit non-zero without output on cancel, and receives `start` as its last argument when one is given. `/providers` reports `folderPicker: true` only when a picker command is available, and the browser shows **Browse…** only then. Only one dialog can be open at a time (409), and a dialog left open for `Agents:FolderPickerTimeoutSeconds` fails with 504. The chosen folder is still validated as a repository root when the connection is saved. Once a folder is entered, `POST /repository-refs` with `{path}` returns `{root, isRoot, current, branches}`: the browser fills **Base Git ref** with the current branch (until you type your own), suggests local branches, and warns when the folder is inside a repository rather than its root. The response also carries `isRepository`, `hasCommits` and `hasFiles`. When a folder is not a repository, or a repository has no commits, the dialog offers **Initialise Git** (or **Create first commit**), which calls `POST /repository-init` with `{path, includeFiles}`. That runs `git init` with your `init.defaultBranch`, `git add --all` only when you tick the option, and an `Initial commit`. Agents start from committed files, so a repository needs at least one commit.

## Model and effort selection

Project connections optionally accept `settings`, a map keyed by provider (`codex`, `claude`, `gemini`) with `{model, effort}` values. Defaults are stored separately for each provider. The existing `model` input/output remains compatible with the preferred provider; a legacy save preserves the other provider's defaults and existing effort. Model IDs remain caller inputs: any ID or alias can be sent. To make choosing one quicker, `GET /providers/{provider}/models` returns `{provider, source, models: [{id, name}], error}`. Codex models come from `codex debug models` (entries with `visibility: list`, in catalogue priority order) and Gemini (Antigravity) models from `agy models`. The Claude CLI cannot list models, so its choices come from `Agents:ConfiguredModels`, with display names in `Agents:ConfiguredModelNames`: aliases such as `opus` (labelled “latest”, always the newest model in that family) and full IDs that pin a version. Each run records `observedModel`, the exact model the agent reported using (Claude names it when its session starts), so an alias's resolution is visible after it runs. Catalogue entries carry `lastRan` when the latest run with that choice used a different model, and `defaultLastRan` gives the same for the agent default. Codex lists only what its installed CLI version knows; update the CLI to see newer models. `source` is `cli`, `configuration` or `none`. A failed or empty listing returns `none` with an `error` and is not cached. Successful listings are cached for `Agents:ModelCatalogueCacheMinutes`, and each CLI call is bounded by `Agents:ModelCatalogueTimeoutSeconds`. The browser offers listed models in a picker beside **Other model…** for a free-text ID. `/providers` supplies configured provider-specific `effortLevels`; supported levels also depend on the selected model and account policy. Configuration provenance is retained beside those levels in `appsettings.json`.

Explicit dispatch accepts optional `model` and `effort` overrides. Omission/null inherits that provider's project defaults; an empty string explicitly uses the agent default. For a follow-up, omission/null inherits the previous run's captured settings, even if project defaults changed. Users can explicitly override settings on a follow-up. Every run stores both the requested overrides and the resolved model/effort, so changing a request ID's settings returns 409 while identical retries keep the original snapshot.

The CLI receives `--model` only for an explicit resolved model. Codex receives effort as `-c model_reasoning_effort="…"`; Claude receives `--effort …`. Unset settings omit those arguments. Run history labels these as requested settings, because provider defaults, aliases and managed policy can change the model/effort actually applied. No inference run is started by saving defaults or editing selection fields.

Codex continuation places configuration overrides on `exec resume` itself. The installed CLI parses resume configuration separately from its parent command; passing sandbox settings only to `exec` can reopen an implementation as read-only. Both initial and resumed writing runs remain read-only, while implementation runs use workspace-write without bypassing sandbox or approval protections.

Factory work can opt into [project model routing and execution budgets](FACTORY-EXECUTION-POLICY.md). Provider completion usage is retained with explicit coverage; `Agents:MaxUsageEvents` and `Agents:MaxOutputCharacters` bound that history. Usage reports do not establish a hard token/currency cap or an account billing total.

## Gemini through Antigravity CLI

The `gemini` provider uses Google's supported Antigravity CLI (`agy`), configured by `Agents:GeminiExecutable` or `Agents__GeminiExecutable`. Run `agy` interactively once to sign in. Google retired the legacy Gemini CLI for individual accounts; pointing this setting at the old `gemini` command will not work with the Antigravity protocol. This integration requires `--input-format stream-json` and session-only `--settings` support, verified with Antigravity CLI 1.4.12. Vendor desktop conversations are not synchronized.

Model IDs are explicit caller inputs; the picker lists the output of `agy models`. An omitted model uses Antigravity's own default, which can be changed outside Planner; enter a Gemini model slug to require a Gemini model. Configured effort levels come from `agy --help` with provenance in `appsettings.json`; actual effort availability depends on the selected model. Independent model/effort defaults are persisted for each provider.

The runner sends one NDJSON `user` message on stdin and closes the pipe after the captured work order. It reads `init`, `step_update` and terminal `result` envelopes, records `conversation_id`, and takes Markdown from the completed result's `response`. Partial activity never establishes success: both terminal status `SUCCESS` and exit code zero are required. Continuation uses `--conversation` with the exact saved ID. Legacy Gemini CLI sessions are incompatible; start a new Antigravity session rather than reusing one.

The terminal `usage` payload is retained verbatim. Antigravity counters are cumulative over the conversation, including continuation, and must not be summed as independent turn totals. Missing counters remain unknown.

Bundled JSON policies are passed through `--settings` for that session only. Read-only work denies file writes, commands, unsandboxed commands, MCP and web actions; it does not rely on planning-mode instructions to enforce read-only access. Implementation uses `--mode accept-edits`, `--sandbox` and `proceed-in-sandbox`; commands needing unavailable sandbox support or outside approval remain denied in headless mode. No permissions-bypass flag is used, and the integration does not change global CLI settings or trusted folders. A selected repository must be trusted in Antigravity before unattended execution. Policies are included in build/publish output. See Google's [headless protocol](https://antigravity.google/docs/cli/headless/), [permissions](https://antigravity.google/docs/permissions?tab=cli) and [Gemini CLI migration](https://antigravity.google/docs/gcli-migration).
